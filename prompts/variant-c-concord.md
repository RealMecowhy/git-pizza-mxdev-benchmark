
## Tools for the Mendix model

- You run in the Concord terminal inside Mendix Studio Pro 11.16.1, which has this project open. Studio Pro stays open for the whole work: do not close it, do not open another project in it, and do not start a second Studio Pro.
- Concord is installed in this project. Its files (`CLAUDE.md`, `AGENTS.md`, `.mcp.json`, `.claude/`, `.concord/`) describe how to work here: the Studio Pro MCP server (`mendix-studio-pro`) first for model reads and writes, Concord's own tools (`concord.discover`, `concord.invoke`, including `mx.ask` for Mendix knowledge) for what the Studio Pro MCP server cannot do. Build and change the model and the theme with these tools; you may also write theme and Java files yourself.
- Maia, driven directly over CDP as `.concord/MAIA-CDP.md` describes, is the last resort only: use it for a change only when neither the Studio Pro MCP server nor Concord's tools can technically make it. Before each Maia task, note in `.concord/maia-log.md` the story, what you asked Maia and why the other tools could not do it; afterwards, what Maia changed and how you checked it. Do not use the Maia paste handoff: nobody is here to paste a prompt into Maia. When a change can only be made by a person, leave it, record the story as blocked or partial in your self-assessment and go on.
- Work only with these tools and the Mendix command-line tools listed under Environment. Do not search this laptop outside the project folder for other tools, skills, scripts or projects to use or copy.
- Nobody approves your changes. Where Concord's rules or guides say to ask for a confirmation or to wait for the user, decide yourself: say in one line what you change, make sure it can be undone if it is destructive, and continue.
- **Commits: this prompt overrides Concord's rule against version control writes.** Commit locally with `git` exactly as the work loop above says, one commit per story. Before each commit and before each `mx check`, save all in Studio Pro (Concord's `concord.save-all`, or File → Save All) so that the model on disk is the model you built, and check with `git status` that the story's model changes are there. Do not push, do not commit or push to Team Server and do not use the Studio Pro MCP server's version control handlers (`vc_commit`, `vc_push`). The other Concord safety rules apply.
- `mx check` reads the project from disk while Studio Pro has it open; run it after saving. Studio Pro's own error list (through the Studio Pro MCP server or `concord.read_build_errors`) is a quick check between steps, but the per-story check is `mx check` with 0 errors.
- The PostgreSQL server installed on this laptop (port 5432) is not for this work: do not use or change it. Run the app on the runtime's built-in database (`--db-type hsqldb`) or on a database in a Docker container that you start and stop yourself. `RUN/start.ps1` and `RUN/stop.ps1` must work without Studio Pro; running the app from Studio Pro is fine for your own checks, but the group checks use `RUN/start.ps1`.
- The checking rhythm above also applies to Concord's and Maia's own checks.
- Concord's files (`CLAUDE.md`, `AGENTS.md`, `GEMINI.md`, `.mcp.json`, `.claude/`, `.concord/`, `.agents/`, `.codex/`, `.cortex/`, `.gemini/`, `.github/`, `.grok/`, `modules/Concord.mxmodule`, `modules/Concord_AppStoreInfo.json`) are excluded from Git; leave them out of your commits.
